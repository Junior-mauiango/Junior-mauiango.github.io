Project overview

The goal of this project was to build a complete embedded vehicle that combined low-level microcontroller control with a higher-level browser interface. The STM32 handled the time-critical hardware functions while the Raspberry Pi provided the user interface and communication layer.

The result was a four-wheel-drive vehicle capable of independent bidirectional motor control, remote browser commands, obstacle protection, battery-voltage monitoring, and real-time system-status reporting.

System architecture

The design separated the system into two main computing platforms. The Raspberry Pi handled the browser dashboard and sent movement commands to the STM32. The STM32 handled the motor-control, sensor, and battery-monitoring functions.

  • Raspberry Pi: browser-based control interface and high-level command generation
  • STM32: bare-metal firmware, motor PWM generation, UART communication, ultrasonic sensing, and ADC battery monitoring
  • Motor-control hardware: four DC motors driven independently in both directions
  • Power system: 3S LiPo battery with DC-DC regulation for the electronics

Bare-metal firmware

STM32 peripherals were configured directly at the register level rather than relying on a high-level hardware abstraction layer.

Browser control

A Raspberry Pi browser dashboard provided movement commands and displayed vehicle direction, PWM duty cycle, obstacle distance, and system status.

Power management

The system used a 3S LiPo battery with regulated power supplied through a DC-DC buck converter and ADC-based battery-voltage monitoring.

Motor-control system

The vehicle required independent bidirectional control of four DC motors. To achieve that, I configured eight PWM outputs across the STM32 TIM2 and TIM3 peripherals using bare-metal register-level C.

Using independent PWM outputs allowed the firmware to control the direction and speed of each motor while keeping the time-critical motor-control behavior on the STM32.

PWM debugging

One of the major debugging challenges appeared when several motor channels did not operate reliably. The issue was traced to incompatible timer-output pins. I diagnosed the problem and rerouted the PWM signals to STM32 pins connected to functional timer channels.

After the signals were reassigned, reliable control was restored across all four motors.

Raspberry Pi communication

The Raspberry Pi communicated with the STM32 through a 115,200-baud UART link. This allowed browser-issued commands to be sent to the microcontroller while keeping the low-level motor control independent from the web interface.

The browser dashboard provided real-time visibility into the vehicle's operation, including direction, PWM duty cycle, obstacle distance, and overall system status.

Obstacle detection

The vehicle included ultrasonic sensing as a safety feature. Distance measurements were used to override forward-drive commands when objects crossed the programmed safety threshold.

This added a layer of protection between the user interface and the motor-control system, allowing the STM32 to prevent unsafe movement even when a forward command was received.

Battery monitoring and power

The vehicle was powered from a 3S LiPo battery. A resistor-divider circuit scaled the battery voltage into the STM32 ADC measurement range so the firmware could monitor the battery during operation.

A low-voltage threshold of 9.9 V was used to protect the LiPo from excessive discharge.

A DC-DC buck converter provided regulated power for the STM32, Raspberry Pi, motor drivers, and supporting electronics.

Final system

The completed system brought together embedded firmware, hardware, communication, sensing, power management, and a browser interface into one working platform.

  • Independent bidirectional control of four DC motors
  • Eight STM32 PWM outputs using TIM2 and TIM3
  • Browser-based vehicle control through a Raspberry Pi
  • 115,200-baud UART communication between Raspberry Pi and STM32
  • Ultrasonic obstacle detection with forward-motion override
  • Real-time dashboard visibility into operating status
  • ADC-based 3S LiPo battery monitoring
  • 9.9 V low-voltage protection threshold
  • DC-DC buck regulation for the control electronics

What I learned

This project gave me experience integrating software and hardware across multiple levels of an embedded system. The most valuable part was working through real hardware problems rather than only writing firmware in isolation.

The PWM pin issue in particular reinforced the importance of understanding the microcontroller's timer-channel and pin-mapping constraints. The project also required coordinating power, communication, sensing, motor control, and user-interface behavior as parts of one complete system.
